# pdf2cbz Local Metadata Investigation

Date: 2026-05-25

## Summary

The dry run exposed a real metadata quality problem. `pdf2cbz` currently lets PDF metadata titles win over better product/file identity in too many cases.

For local/non-Humble PDFs this is especially bad because there is no Humble product title to fall back to. Many PDFs carry internal titles from source art, cover files, layout pages, UUIDs, or generic print presets. The visible filename is usually a better product title than the PDF metadata.

The same issue also affects Humble-matched PDFs: `buildComicInfoFields` currently prefers `enrichedFile.title.value` over the Humble product title, so some Humble CBZs would get titles like `FrontCover_image.eps`, `Untitled`, or barcode/license strings.

## Current Selection Flow

```text
PDF path
  |
  v
enriched-metadata file lookup
  |
  +-- matched to Humble? ---- yes ----> Title = enriched title, else Humble product title
  |
  +-- no Humble match ------ local ---> Title = enriched title, else filename stem
```

The fragile step is `enriched title`.

```text
enriched title
  |
  v
buildTitleField()
  |
  +-- epub:dc:title
  |
  +-- xmp:dc:title
  |
  +-- ignores pdf-info:Title
  |
  +-- no title junk rejection
```

Relevant code:

- `src/download/enriched-metadata.ts`: `buildTitleField` accepts EPUB/XMP titles, gives them confidence `0.75`, and does not reject generic/junk titles.
- `src/cli/commands/pdf2cbz.ts`: `buildComicInfoFields` uses `enrichedFile?.title?.value` before Humble product metadata.
- `src/cli/commands/pdf2cbz.ts`: `buildLocalProductIdentity` uses `enrichedFile?.title?.value` before the filename stem.

## Root Cause

```text
Bad title source:
  PDF/XMP dc:title is often not a publication title.

Missing guardrails:
  title extraction has no reject list, no confidence downgrade for asset-like values,
  and no special handling for repeated XMP title arrays.

Wrong precedence:
  Humble product titles and local filenames are more reliable than PDF titles,
  but current pdf2cbz precedence lets PDF titles override them.
```

The implementation borrowed title handling from enrichment, where preserving metadata evidence is useful. But `pdf2cbz` is using that evidence as product identity. Those are different jobs.

## Recommended Fix

### 1. Separate Evidence From Product Identity

Keep raw PDF metadata in `enriched-metadata.json`, but do not treat `enrichedFile.title` as authoritative for product identity.

```text
metadata evidence       -> enriched-metadata.json
product identity        -> Humble product title or local filename-derived title
ComicInfo display title -> conservative product identity
```

### 2. Humble PDFs Should Prefer Humble Product Title

For Humble-matched PDFs:

```text
Title  = Humble product title
Series = Humble product title, or later a separate series parser
```

Optionally record the PDF metadata title in `Notes` only when it differs and passes quality checks.

### 3. Local PDFs Should Prefer Filename Stem

For unmatched local PDFs:

```text
Title  = cleaned filename stem
Series = parent folder
```

Only use PDF title metadata when it passes stricter quality checks and looks better than the filename.

Suggested conservative v1:

```text
Always use filename stem for local productTitle.
Keep PDF title metadata only in metadataSources/evidence.
```

That would turn:

```text
local product "Print", series: Space Between
```

into:

```text
local product "Afterglow Digital Copy", series: Space Between
```

### 4. Add Title Rejection For Metadata Evidence

Even if product identity stops trusting PDF titles, `enriched-metadata.json` should mark junk titles as rejected so future callers do not repeat this mistake.

Reject or downgrade title values matching:

```text
Untitled
Print
*.eps
*.indd
UUIDs
logo / cover / frontcover / image
barcode / licensed strings
page names like Page008
layout names like *_LTR, *_COVERA, *_DS_logo
tool/vendor URLs
```

### 5. Reconsider `pdf-info:Title`

`pdf-info:Title` is currently extracted but ignored by `buildTitleField`.

That is not automatically safer than XMP. Examples show both good and bad values:

```text
good-ish: Sharp Dreams 01 - PDF
bad:      Summoned_Cthulhu_03_COVERA
bad:      70665132-1cad-4d0d-a53b-8417acb429b3
```

So it should not be blindly preferred, but it can be considered after quality filtering.

## Proposed Product Identity Flow

```text
PDF path
  |
  v
is Humble match?
  |
  +-- yes --> productTitle = Humble product title
  |          series       = Humble product title for now
  |          publisher    = enriched publisher if accepted
  |
  +-- no ---> productTitle = cleaned filename stem
             series       = parent folder
             publisher    = enriched publisher if accepted
```

Optional future enhancement:

```text
filename parser
  |
  +-- "Title Vol 1 Digital" -> Title = "Title Vol 1"
  +-- "Title #1"            -> Series = "Title", Number = "1"
  +-- "Title Volume 03"     -> Series = "Title", Volume = "03"
```

## Impact On The Current Dry Run

The dry run behavior is mechanically correct: local products are detected, can be archived, and are reported.

The title source is not acceptable:

```text
current:
  local product "Print", series: Space Between
  local product "Summoned_Cthulhu_03_COVERA", series: Space Between

recommended:
  local product "Afterglow Digital Copy", series: Space Between
  local product "Dragon Guardian Elodea 01 - Digital", series: Space Between
```

## Recommendation

Fix `pdf2cbz` title precedence before doing a real conversion/archive run.

The safest immediate change is:

```text
Humble products: use Humble product title.
Local products: use filename stem.
Metadata titles: keep as evidence, not identity.
```

That preserves the valuable metadata extraction work while preventing low-quality embedded PDF metadata from polluting `ComicInfo.xml` and transform cache identity.
